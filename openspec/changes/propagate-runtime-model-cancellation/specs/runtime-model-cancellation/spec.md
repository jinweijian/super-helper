## ADDED Requirements

### Requirement: 回合模型取消传递

系统 SHALL 将当前回合的取消信号传递给每个在线模型消费者及其嵌套审核，不使用跨回合共享可变信号。

#### Scenario: Preflight 正文尚未完成
- **WHEN** 正式 runtime 的模型 Preflight 已收到 HTTP 响应头而正文未完成，用户停止该回合
- **THEN** adapter 中止读取，runtime 完成取消收尾，不等待模型请求原超时，不启动后续模型或 Worker。

#### Scenario: 并发 Case 与后续回合
- **WHEN** 两个 Case 同时调用模型，其中一个被取消，或旧消息的取消请求在新回合开始后到达
- **THEN** 仅正确绑定的回合受影响，其他 Case 与后续回合正常完成。

### Requirement: 取消后不新增模型工作

系统 SHALL 在请求前和返回后检查取消，取消不得通过错误降级路径触发新的模型请求。

#### Scenario: 嵌套调用与迟到成功
- **WHEN** 取消发生在第一个模型完成与嵌套审核之间，或自定义模型忽略 signal 后迟到返回
- **THEN** 不启动下一模型调用，不将迟到未审核内容提升为结论。

#### Scenario: 正常错误与缺省调用
- **WHEN** 未取消但模型限流、响应不合法、未配置模型，或直接消费者未传可选信号
- **THEN** 原有安全降级及调用兼容保持，不泄漏原始错误正文。

### Requirement: 保留已接受结果并唯一收尾

系统 SHALL 保留本回合取消前已接受的事实与推断，明确为初步判断；无可接受结果时只输出取消说明，清理回合控制。

#### Scenario: 表达中取消
- **WHEN** claims 已被冻结但 presentation 模型尚未完成时取消
- **THEN** 不继续请求模型，以确定性表达返回已接受内容和边界，同一消息只收到一个 helper 回复。

#### Scenario: 尚未审核与资源清理
- **WHEN** 取消发生在证据尚未审核阶段，或回合正常完成/异常退出
- **THEN** 未审核证据不成为最终结论，回合控制正确清理，既有 Case JSON 和历史消息不被破坏。
